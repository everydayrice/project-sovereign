# Project Sovereign V0.2 Remaining Work

This is the exact continuation queue after the Control Plane and product-alpha local slices. It is ordered to turn the proven in-memory lifecycle into a secure alpha, not to expand V1 scope indiscriminately.

## Completed locally; not yet activated in infrastructure

- The Console shell and its core navigation now exist with a public, fail-closed account entry surface.
- Source lifecycle, direct-upload metadata, initialization coverage, Candidate Intelligence, Canonical Change Sets/Checkpoints/reverts, recovery snapshots, and bounded correction/improvement records are implemented against the deterministic in-memory adapter.
- `0002_product_alpha.sql` describes their Neon shape; it has **not** been run.
- Google Drive and GitHub are connector declarations only. No OAuth authorization or provider data access has been claimed.

## Required before any real alpha deployment

1. **Provision and verify dedicated infrastructure.** Confirm Project Sovereign’s dedicated Cloudflare Worker, PROJECT SOVEREIGN Neon project, R2 bucket, Neon Auth issuer/JWKS, and scoped secrets. Do not reuse RICE Lightning or RICE Command runtime resources.
2. **Implement Neon Auth verification.** Replace `failClosedAuthenticator` with JWT/JWKS validation, subject-to-Principal resolution, tenant membership/role checks, and revocation handling. Keep all Gateway routes fail-closed on any uncertainty.
3. **Run and verify `0001_foundation.sql`.** Execute only against the dedicated Neon project, verify RLS transaction settings, then add an integration test suite against an ephemeral/non-production Neon database.
4. **Replace the in-memory store.** Build transaction-scoped Neon repositories for Command, Control Plane, Continuity, Extensions, and Audit. The existing services must retain the same contracts and collision semantics.
5. **Bind R2 intentionally.** Add source-import and artifact adapters with encrypted object references, data classification, retention enforcement, content fingerprints, and deletion/retention audit behavior.

## V0.2 core completion after persistence

6. **Command completion.** Persist workspace containment, then add role/permission evaluation, approval workflow, tenant policy registry/editor, source authority configuration, and provider/agent/tool registry UI/API. Tenant remains the hard isolation boundary.
7. **Intelligence completion.** Replace the product-alpha in-memory implementation with canonical record/revision/provenance/relation repositories, policy-controlled proposal/review/promotion, source resolution, live-authority freshness checks, and rebuildable retrieval indexes. Do not auto-promote Continuity.
8. **Source and initialization activation.** Bind direct upload to R2 with retention/audit controls; implement one real OAuth connector; add inventory/analysis jobs and source failure/retry semantics; retain the present honest coverage model.
9. **Continuity completion.** Persist Session Capsules, Candidate Memories, richer handoff acceptance/completion, task state transitions, waiting/snooze, and governed artifact links.
10. **Control Plane hardening.** Add Command-configured collision rules and approvals, policy audit detail, resource locator adapters, notification/webhook events, bounded stale-claim confirmation flows, and telemetry. Do not convert planned claims into global locks or auto-minimize actor context.
11. **Gateway parity.** Add MCP transport and CLI/admin tooling over the same services/endpoints; publish the JSON Schema/OpenAPI validation pipeline and version-negotiation behavior.
12. **Console activation.** Bind the current views to persistent repositories and real Neon Auth; add the reviewed setup, source connection, upload, initialization/review, canonical approval, recovery, and audit interactions. Queue and Ideas remain external extensions.
13. **Extension Host completion.** Persist private/manual installation, grant/revoke credentials, event subscriptions/webhooks, launch metadata, uninstall retention actions, and audit. Do not build a public marketplace in V0.2.

## RICE alpha migration — only after core persistence and review

14. Build a read-only, exportable `rice-command` migration adapter with source repository/path/commit provenance.
15. Stage records by canonical Intelligence, Continuity, source/live authority, and superseded/obsolete history; require review before promotion.
16. Import into the RICE tenant configuration without adding RICE identifiers to generic schemas. Verify rollback/export and compare orientation-first retrieval with the former automatic-minimum-context behavior.
17. Run the real ChatGPT/Work/Codex bridge against actual concurrent sessions and repositories; measure collisions, handoff completeness, requested context depth, latency, rework, and acceptance before changing any default traffic or context policy.

## Explicitly out of V0.2 core

- Queue Tracker and Idea Tracker product UIs;
- Workforce;
- persistent Compute/workspace execution;
- a public extension marketplace;
- automatic context starvation/hidden minimum-context policy;
- generic deployment of RICE Command history without review.
