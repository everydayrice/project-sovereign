# Project Sovereign V0.2 Product-Alpha Slice

This document records the implemented, deliberately bounded bridge from the V0.2 Control Plane foundation to a usable V1-alpha product. It is additive to the V0.1 freeze and the current V1 architecture; it does not introduce a module or rename an approved primitive.

## What is now executable locally

- Public landing, sign-in, and sign-up routes present an honest configuration state. Protected operations remain unavailable until Neon Auth is configured; the product does not silently create unauthenticated accounts or tenants.
- The authenticated Console has Home, Command, Intelligence, Control Plane, Continuity, Sources / Storage, Integrations, Extensions, and Audit / Health navigation. The views surface readiness, canonical history, source health, initialization coverage, traffic, continuity, recovery, and audit state.
- Command supports tenant-contained workspaces. Tenant remains the hard security boundary; a workspace is organizational containment, not a cross-tenant authority boundary.
- The Source Registry distinguishes connector declaration from connection, and source connection from inventory/analysis/currentness. Google Drive and GitHub are declared OAuth connector contracts only; no provider access is implied. Direct upload creates a Sovereign-managed source/item reference with `awaiting_object_store`, not a false claim that R2 has stored bytes.
- Initialize, Study, and Sweep are explicit runs with per-source outcomes and measurable coverage. A partial, blocked, or failed source yields partial coverage rather than a false completion state.
- Canonical Intelligence has Candidate Intelligence, reviewable Canonical Change Sets, immutable record revisions, automatic readable Canonical Checkpoints, supersession, tenant-scoped status, and non-destructive revert. A revert that conflicts with a later change is stopped for reconciliation instead of silently creating contradictory active records.
- Trust Recovery captures a scope/revision snapshot, pauses risky canonical automation for the recovery session, reports source/canonical/initialization health, records a bounded correction/improvement candidate, and completes without deleting history.

## Deliberate activation boundaries

The Worker composition remains an in-memory test adapter. The production Worker fails closed for every protected route until a real Neon Auth verifier is installed. No deployment, Neon migration execution, R2 storage write, OAuth connection, external source synchronization, or Resend configuration is claimed by this slice.

`db/migrations/0002_product_alpha.sql` is the target Neon shape after `0001_foundation.sql`. It adds source lifecycle/item metadata, tenant workspaces, canonical history/change-set/checkpoint tables, initialization state, recovery, and failure-learning records. It must be reviewed and run only on the dedicated PROJECT SOVEREIGN Neon project with the transaction-local tenant/RLS rules active.

## Product-alpha HTTP seam

The same verified Gateway identity drives the Console and JSON routes. The implemented seam is intentionally provider-neutral:

- `GET/POST /v1/command/workspaces`
- `GET /v1/sources/connectors`, `GET/POST /v1/sources`, `POST /v1/sources/uploads`, inventory/failure subroutes
- `POST/GET /v1/initialization/runs` and source-result/complete subroutes
- canonical status, record, Candidate Intelligence, Change Set approve/reject/revert, and understanding routes under `/v1/intelligence`
- recovery and correction/improvement routes under `/v1/recovery` and `/v1/improvement`
- the existing Control Plane/Continuity routes and `GET /v1/console/snapshot`

`contracts/v0.2/product-alpha.schema.json` defines the additive object shapes. The older OpenAPI document remains the stable Control Plane transport contract; it should be expanded and validated with the production auth/persistence adapter rather than representing unconfigured OAuth or storage as live.
