# Project Sovereign V1

## Objective

Ship a complete internal alpha of Sovereign core for one real tenant (RICE) without hard-coding RICE into the product model.

V1 must prove that a user can persist intelligence and continuity across AI providers, receive a fast authoritative orientation map, let the authorized agent choose its own context appetite, coordinate concurrent actors before they collide on shared resources, inspect where context came from, and preserve material changes through governed promotion.

## Core platform only

V1 includes the four core modules:

- COMMAND
- INTELLIGENCE
- CONTROL PLANE
- CONTINUITY

It also includes the Protocol, Gateway, Console, Security, Sync, Efficiency telemetry and Extension Host required to operate those modules.

V1 does **not** include Queue Tracker, Idea Tracker, Workforce or Compute as built-in core products. Those are external extensions/add-ons.

## Infrastructure

Project Sovereign owns its own independent infrastructure:

- GitHub repository: `everydayrice/project-sovereign`
- Cloudflare Worker: dedicated Project Sovereign runtime
- Neon project: dedicated Project Sovereign database
- Cloudflare R2 bucket: dedicated Project Sovereign object/source storage
- Neon Auth for authentication

RICE is the first tenant and alpha tester.

## CONTROL PLANE V1

Control Plane is orientation-first, traffic-aware and lightweight.

It provides:

- tenant/actor/task/scope orientation;
- relevant entity/project/domain pointers;
- authority/source map;
- privacy/permission/policy boundaries;
- freshness/volatility markers;
- pointers to relevant Intelligence;
- pointers to relevant Continuity/session/task state;
- pointers to relevant live systems and extensions;
- agent/model/tool capability and route options;
- compact orientation packet;
- deterministic packet revision/hash;
- route/orientation trace;
- Traffic Session check-in/check-out;
- Resource Claims with resource, intent, scope, branch/worktree/environment/path where relevant;
- current traffic returned with orientation/resource requests;
- collision classification (`shared`, `caution`, `exclusive`/approval-gated according to Command policy);
- heartbeats/lease TTLs/stale-session recovery;
- traffic re-evaluation when an actor changes or activates resources;
- checkpoint integration and artifact/outcome reporting on checkout.

It does **not** automatically decide the agent's minimum necessary context or hide authorized context behind a platform-selected relevance threshold.

After receiving the orientation packet, the agent/user selects its own context appetite and may retrieve narrowly, broadly or deeply from authorized Intelligence, Continuity and live/source systems.

V1 may expose optional convenience appetite modes such as `lean`, `standard`, `broad`, `deep` or explicit retrieval requests, but the requesting agent/user controls the choice. The platform only enforces Command policy, permissions, privacy boundaries, explicit tenant resource ceilings and hard technical service limits.

Traffic coordination follows [`TRAFFIC-CONTROL.md`](TRAFFIC-CONTROL.md). The V1 objective is collision awareness before broad hard locking: reads and independent branches can coexist; dangerous same-target operations can warn, require approval or reserve exclusivity according to Command policy.

- authority/provenance;

## Console V1

One human-facing shell:

- Home
- Command
- Intelligence
- Control Plane
- Continuity
- Extensions
- Integrations
- Audit / Health

The Console may show basic Continuity object inspectors, but specialized workflow UIs remain extensions.

The Control Plane screen should show the terrain/authority/source map **and live traffic board**: active actors, resources, intent, claim state, last heartbeat/checkpoint, warnings/collisions and stale sessions. It should not pretend that an automatically minimized context bundle is inherently optimal.

## Efficiency V1

V1 should **observe before optimizing**.

Measure:

- orientation packet size;
- context bytes/tokens later requested by the agent;
- depth/breadth chosen by the agent;
- sources/records actually used;
- duplicate context encountered/suppressed;
- unchanged context that could be skipped;
- cache hits;
- route recommendation/selection;
- retries/escalations;
- task corrections/rework where measurable;
- estimated model-input cost where pricing is known;
- request latency where available;
- concurrent Traffic Sessions;
- collision warnings and their outcomes;
- safe concurrent operations;
- stale/abandoned claims;
- conflicts prevented or surfaced before merge/deploy/migration.

Caching, deduplication and known-context delta delivery may be offered when they preserve requested information. V1 must not automatically starve an agent of context merely to reduce token usage.

Once enough real alpha data exists, Sovereign can recommend appetite/routing defaults and later optionally automate them if the tenant enables that behavior through Command. Traffic policy can similarly become more sophisticated based on observed safe/conflicting concurrency patterns.

Efficiency remains a cross-cutting capability, not a module.

## RICE alpha migration

Build an explicit migration/import adapter from `everydayrice/rice-command`.

The migration must:

1. preserve repository/path/commit provenance;
2. distinguish canonical records from working/task/session state;
3. preserve source authority metadata;
4. avoid blindly copying obsolete/superseded records as current;
5. map RICE-specific identifiers through tenant-scoped configuration;
6. allow validation before final promotion/import;
7. retain export/rollback paths;
8. never make existing RICE Command history disappear merely because Sovereign becomes the new operational platform.

The current RICE Control Plane's automatic minimum-sufficient retrieval behavior is migration evidence, not a requirement for Sovereign. The RICE alpha should specifically compare the new orientation-first/agent-directed approach against the old behavior.

## V1 success criteria

V1 is successful when:

1. RICE can authenticate as the first tenant and operate a personalized RICE COMMAND instance.
2. A supported AI agent can connect through MCP or HTTP, receive a fast Sovereign orientation packet and independently request the amount/depth of authorized context it needs without knowing storage internals.
3. The same durable Intelligence is reusable across at least two distinct agent/provider surfaces.
4. Session/Task continuity can be resumed after the original AI session is gone.
5. Working state is never silently treated as canonical truth.
6. A material candidate can be proposed, reviewed/promoted according to Command policy, and read back with provenance/audit history.
7. The Control Plane clearly maps relevant domains, authorities, sources, continuity and available routes without silently rationing the agent's context.
8. Two simultaneous agents can check in against overlapping resources and both receive accurate current traffic before mutation.
9. In the alpha concurrency scenario, an agent planning repo A while another agent is active there receives the warning/state, and traffic is re-evaluated when that planned claim becomes active after work on another resource.
10. Checkpoints and checkouts update/release claims; abandoned sessions become stale through leases rather than remaining permanent locks.
11. Command policy can distinguish safe shared reads/independent branches from cautionary overlap and exclusive critical sections such as same-branch writes, production deploys or migrations.
12. RICE Lightning Queue Tracker can install as an external extension and work through normal scoped APIs/events rather than hidden first-party access.
13. Revoking the Queue extension stops its access without damaging Sovereign core data.
14. Runtime indexes/caches can be rebuilt without losing canonical Intelligence or Continuity source state.
15. Alpha telemetry is sufficient to compare task quality, context usage, rework and concurrency/collision behavior before any automatic minimization or aggressive locking policy is introduced.
